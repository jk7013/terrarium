# Terrarium 작업 로드맵

작성일: 2026-07-29

이 문서는 Terrarium에 필요한 작업을 안전한 순서대로 하나씩 처리하기 위한 체크리스트다.
새 기능을 무작정 추가하기보다, 먼저 데이터가 망가지지 않고 검색이 안정적으로 동작하는 기반을 만든다.

## 1. 이 문서를 사용하는 방법

- 위에서 아래 순서대로 진행한다.
- 한 번에 한 작업 묶음만 진행한다.
- 작업 묶음마다 별도 브랜치와 별도 커밋을 사용한다.
- 작업을 시작하기 전에 현재 데이터 수와 검색 결과를 기록한다.
- 작업이 끝나면 테스트, 실제 실행 확인, 결과 기록을 모두 마친다.
- 완료 조건을 전부 만족해야 체크박스를 완료 처리한다.

표시 방법:

- `[ ]` 아직 시작하지 않음
- `[x]` 완료
- `P0` 다른 기능보다 먼저 해결해야 하는 작업
- `P1` P0 다음에 해결할 중요한 작업
- `P2` 기반이 안정된 뒤 진행할 개선 작업

작업량 표기:

- `S`: 작은 작업
- `M`: 중간 크기 작업
- `L`: 여러 단계로 나누어야 하는 큰 작업

## 2. Terrarium을 아주 간단히 설명하면

Terrarium은 다음 순서로 일한다.

1. 문서를 받는다.
2. 문서를 검색하기 좋은 작은 조각인 `청크(chunk)`로 나눈다.
3. 각 청크를 숫자 형태인 `임베딩(embedding)`으로 바꿔 데이터베이스에 저장한다.
4. 질문이 들어오면 관련 청크를 찾는다.
5. 필요하면 검색 결과의 순서를 다시 판단하는 `리랭커(reranker)`를 사용한다.
6. 검색 결과를 Jido나 다른 클라이언트에 돌려준다.

현재 가장 큰 문제는 4번의 검색 알고리즘보다 1~3번의 문서 관리와 전체 서비스 안정성이다.

## 3. 항상 지켜야 할 안전 규칙

- 운영 데이터베이스에서 전체 색인을 한 번에 삭제하는 기능을 사용하지 않는다.
- `law_article` 데이터를 수정하는 작업은 별도 작업으로 분리한다.
- 삭제나 교체는 반드시 특정 source 하나만 대상으로 한다.
- 삭제 전에 대상 문서 수와 청크 수를 먼저 보여준다.
- 데이터 변경 전후의 문서 수와 청크 수를 기록한다.
- 색인 실패 시 기존 데이터가 그대로 남도록 만든다.
- 테스트에서 운영 데이터베이스와 운영 Docker volume을 사용하지 않는다.
- 로그나 보고서에 비공개 문서 본문을 넣지 않는다.
- Terrarium 작업과 Jido 작업의 커밋을 섞지 않는다.

# 단계 1. 문서를 안전하게 넣고 교체하고 삭제하기

## T1-1. 전체 삭제 기능을 일반 API에서 제거하기

- 우선순위: `P0`
- 작업량: `S`

### 왜 필요한가

현재 `/api/index` 요청의 `rebuild=true`는 전체 documents, chunks, 검색 로그를 지울 수 있다.
한 번의 잘못된 요청으로 다른 corpus까지 삭제될 수 있다.

### 할 일

- [ ] `IndexRequest`에서 `rebuild` 파라미터를 제거한다.
- [ ] HTTP API에서 전체 초기화를 호출할 수 없게 만든다.
- [ ] 정말 필요한 전체 초기화는 별도 관리 스크립트로만 제공한다.
- [ ] 전체 초기화 스크립트는 명시적인 확인 절차를 요구하게 만든다.
- [ ] 기존 클라이언트가 `rebuild`를 보내면 분명한 오류를 돌려준다.

### 완료 조건

- [ ] `/api/index`로 전체 corpus를 삭제할 수 없다.
- [ ] 잘못된 요청이 다른 source 데이터를 변경하지 않는다.
- [ ] 관련 테스트가 통과한다.

## T1-2. corpus 목록을 관리하는 장부 만들기

- 우선순위: `P0`
- 작업량: `M`

### 왜 필요한가

현재 source는 청크의 문자열 태그로만 존재한다.
Terrarium은 어떤 corpus가 있는지, 몇 문서인지, 어떤 설정으로 색인했는지 알기 어렵다.

### 만들 기능

`corpora` 장부에는 최소한 다음 정보를 저장한다.

- source ID: 예) `mdn_http`
- 화면에 보여줄 이름
- 상태: 준비 중, 사용 가능, 실패
- 문서 수와 청크 수
- 임베딩 모델과 차원
- 청크 크기와 겹침 크기
- 원본 또는 라이선스 정보
- 마지막 색인 시간
- corpus 버전

### 할 일

- [ ] `corpora` 테이블 설계를 작성한다.
- [ ] DB migration을 만든다.
- [ ] 기존 `mdn_http` 데이터를 장부에 연결한다.
- [ ] corpus 목록과 통계를 조회하는 API를 만든다.
- [ ] 존재하지 않는 source 요청에는 분명한 오류를 돌려준다.

### 완료 조건

- [ ] Terrarium에 어떤 corpus가 있는지 API로 확인할 수 있다.
- [ ] 각 corpus의 문서 수와 청크 수를 확인할 수 있다.
- [ ] 같은 차원이지만 다른 임베딩 모델로 만든 데이터가 섞이지 않는다.

## T1-3. source 단위의 안전한 교체 기능 만들기

- 우선순위: `P0`
- 작업량: `L`

### 왜 필요한가

기존 문서를 다시 색인할 때 새 청크 수가 줄어들면 과거 청크가 남을 수 있다.
색인 중 오류가 나면 문서 일부만 저장된 상태가 될 수도 있다.

### 원하는 동작

```text
새 corpus를 임시 공간에 저장
→ 문서 수, 청크 수, 태그, 임베딩을 검사
→ 모두 정상이면 기존 source와 한 번에 교체
→ 실패하면 임시 데이터만 버리고 기존 source는 유지
```

### 할 일

- [ ] `append`, `replace` 동작을 구분한다.
- [ ] 새 데이터를 staging 영역에 먼저 저장한다.
- [ ] 모든 데이터가 정상일 때만 실제 corpus로 전환한다.
- [ ] 기존 문서보다 청크 수가 줄면 남은 옛 청크를 삭제한다.
- [ ] corpus마다 doc ID 공간을 분리해 ID 충돌을 막는다.
- [ ] 실패 시 기존 데이터가 보존되는지 테스트한다.
- [ ] 같은 요청을 다시 실행해도 중복 데이터가 생기지 않게 한다.

### 완료 조건

- [ ] 색인 도중 실패해도 기존 corpus 검색이 정상 동작한다.
- [ ] 문서 재색인 후 과거 청크가 남지 않는다.
- [ ] 서로 다른 corpus가 같은 doc ID를 사용해도 충돌하지 않는다.

### 왜 필요한가

### 할 일

- [ ] 질문 길이의 최소값과 최대값을 정한다.
- [ ] `raw_text` 최대 크기를 정한다.
- [ ] `top_k`와 `final_contexts` 범위를 정한다.
- [ ] source와 profile 값을 검증한다.
- [ ] 잘못된 요청에는 HTTP 400 또는 422를 돌려준다.

### 완료 조건

- [ ] 잘못된 값이 조용히 default 값으로 바뀌지 않는다.
- [ ] 클라이언트가 오류 원인을 이해할 수 있다.

## T2-2. chat, corpus, ephemeral 모드를 명확히 분리하기

- 우선순위: `P0`
- 작업량: `M`

- `corpus`: 선택한 corpus를 검색한 뒤 답변

- [ ] ephemeral에서는 DB corpus 검색을 하지 않는다.
- [ ] corpus 모드에서는 source가 존재하는지 확인한다.
- [ ] raw text가 없는데 ephemeral을 요청하면 오류를 돌려준다.

### 완료 조건

- [ ] 각 모드가 설명과 동일하게 동작한다.
- [ ] ephemeral 결과에 DB corpus 내용이 섞이지 않는다.
